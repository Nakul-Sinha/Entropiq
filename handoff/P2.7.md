- Definitions as built (module docstring of `build.py`):
  - T = `snapshot.time`; the state at T is the tree of `snapshot.sha`; history up to T = non-merge commits reachable from `snapshot.sha` (section 15.5), `reachable_shas(repo_dir, snapshot.sha)` unless the caller passes `reachable`. Every component (lineage, evolution, ownership, co-change, defect history) gets the same set.
  - Files: every regular file at T with a language plugin; `skip_reason` first, then the parse (through the cache, limit `settings.parse_timeout_s`). Parsed files are split with `tdp_core.parsing.is_test_file`; every parsed non-test file is a row.
  - Static family from `FileSyntax`: `cc_sum = module_cc + sum(cyclomatic)`, `cc_mean` over functions (0 without), `cc_max`, `cog_max`, `nesting_max`, `params_max`, `longest_function` (`end_line - start_line + 1`) as maxima over functions (0 without), `n_functions`, `n_classes`, `sloc`, and `dup_ratio` from `clone_stats` over the rows only.
  - `rel_churn_decayed = churn_decayed / max(sloc, 1)`.
  - `cc_trend`: least-squares slope of `cc_sum` against nominal offsets 0, -90, -180, -270, -360 days expressed in years of 365.25 days (unit: cyclomatic complexity per year). The state at T - 90 k days is `git rev-list -1 --first-parent --before="@<ts> +0000" <snapshot.sha>` (a commit exactly at that time counts). A version is found under the current path, else under the first other lineage name (sorted) with the same language plugin. Older versions are filtered by `skip_reason` under their old name (a `(name, blob)` pair already parsed at T is not re-checked) and parsed through the cache; missing, skipped, timed-out or failed versions are dropped; fewer than two versions give 0.
  - SATD: candidates are `satd_candidates(syntax.comments)`; for each row with candidates, one `git -c blame.ignoreRevsFile= -c diff.algorithm=myers --literal-pathspecs blame --line-porcelain -w -L a,b ... <snapshot.sha> -- <path>` on the candidate lines (at most 200 line runs per call), age = (T - author time) / 86,400 days, then `satd_features(syntax, satd_model, ages)`. Blame runs in a thread pool of `min(workers, files)` threads. A blame failure or a non-UTF-8 name logs a warning and gives unknown ages (age 0, count kept).
  - Defect history: `defect_history_features(hist, snapshot, lineage, rows, bugfix, szz, reachable_T=reach, max_fixes=settings.inference_szz_max_fixes)`; zeros without tables.
  - Percentiles: `pct_<f> = base[f].rank(pct=True, method="average")` on the stored float32 values, for every non-binary feature. Any non-finite value or a column set different from `FEATURE_COLUMNS` raises `RuntimeError` (explicit checks, not asserts).
- Parse cache and time limit (module docstring of `cache.py`):
  - `parse_blobs` de-duplicates tasks by key, looks each key up in the cache (a hit counts only when its `language` matches the task's plugin), parses the misses, stores new successful parses, and never caches timeouts or failures (each is logged as a warning). Any exception in a parser (recursion and memory errors included) gives `parse_failed` for that file only. A cache whose `get` or `put` raises is logged once (warning) and not used again during that call; the results equal a build without a cache.
  - Misses are parsed in this process unless `min(jobs, misses // 500) >= 2` and the process may start children (not inside a daemonic process such as a Celery prefork worker). In-process the limit is soft: the parse finishes and its result is dropped as `timeout` when it took longer than the limit. The pool uses `spawn` on every platform, one task at a time per worker, and kills a worker that passes its deadline (hard limit) or dies (`parse_failed`, not retried), starting a replacement while work is pending. If a worker cannot start, does not report ready within 120 s, or misbehaves, every worker is stopped and the files without a result are parsed in-process. No worker outlives the call.
  - `DiskStaticCache` writes `root/<sha[:2]>/<sha>.<EXTRACTOR_VERSION>.json.gz` (section 3.4) holding `{"format": 1, "extractor_version", "blob_sha", "syntax"}`, gzip with `mtime=0` (identical input gives identical bytes), via a unique `.tmp` file and `os.replace`. Reads validate the wrapper and decode with `syntax_from_json`; anything invalid is a miss. Shas must be full lowercase hex (40 or 64), otherwise `ValueError` (no path tricks). I/O errors are logged at debug level and never raised.
- Deviations from the plan and why (D1 to D16):
  - D1. History is always the reachable set (section 15.5); `reachable` lets P2.8 pass the `reachable_T` it already has. At inference a history mined from the analysed sha makes the set every mined commit, as 15.5 requires.
  - D2. Lineage comes from the reachable commits with `until` = their newest author time (`until = T` would drop reachable commits authored after T, see P1.5 and P2.1). `BuildResult.lineage` is the full `path_lineage` output, as P2.6 asks.
  - D3. One test predicate, `tdp_core.parsing.is_test_file`, for the row split, the import graph and co-change.
  - D4. Older `cc_trend` states are first-parent ancestors of `snapshot.sha` by committer date, not `snapshot_at`: `snapshot_at(repo_dir=...)` walks HEAD's branch (wrong for an analysed commit off the default branch) and the old mode uses author dates (leaky). For training snapshots both give the same commits (the snapshot sha is on the default branch's first-parent chain and every commit above it is newer than T).
  - D5. `cc_trend` uses nominal x offsets in years, versions found through lineage names, older versions filtered by `skip_reason` under their old name; missing versions are dropped; one version gives 0.
  - D6. Static maxima are over functions only and 0 without functions (P4.1 costs complexity over functions); module-level code only counts in `cc_sum`.
  - D7. `dup_ratio` from `clone_stats` over the non-test rows only (plan text); `BuildResult.clones` exposes those stats so cost estimates match `dup_ratio`.
  - D8. `bugfix` and `szz` must be passed together (`ValueError` otherwise; an empty `SZZ_SCHEMA` table gives `prior_latent_bugs = 0`). `max_fixes = settings.inference_szz_max_fixes` for train/serve parity (P2.6 note).
  - D9. SATD blame: one call per file with candidates, candidate lines only, every regex candidate (the classifier only changes which ages count), `-w`, pinned config, non-UTF-8 names skipped, failures treated as unknown ages.
  - D10. Percentiles are computed on the float32 values, so `pct_` columns can be recomputed exactly from stored rows (same as P3.0's synthetic data).
  - D11. Process pool only for large batches, soft limit in-process (both modes skip the same files), daemon fallback and start-up fallback; `jobs = 0` still means `os.cpu_count()` and also bounds the blame threads.
  - D12. Cache: fast validated decoder (from_jsonable takes 6.08 s for pylint's 2,356 cached parses, `syntax_from_json` 0.22 s), self-describing wrapper, deterministic gzip, atomic best-effort writes, sha validation, re-pathing of hits, language check.
  - D13. Additive API only: keywords `reachable` and `on_stage`; fields `clones` and `timings_s`; public helpers `static_features`, `cc_sum`, `trend_slope`, `syntax_to_json`, `syntax_from_json`, `ParseTask`, `parse_blobs` and the constants.
  - D14. New skip reason `parse_failed` next to the plan's `timeout`.
  - D15. Extra test module `tests/features/test_static_cache.py` for `cache.py`; branch name from the orchestrator (`step/P2.7-feature-assembly`).
  - D16. A cache that raises is dropped for the rest of a `parse_blobs` call after one warning. P5.1's merged `PostgresStaticCache` lets database errors propagate, and a cache only saves time, so an outage slows a build down instead of failing it.

  - **Why warm can be slower than cold here:** on this laptop the first read of a freshly written file is slow (real-time antivirus scanning). For pylint's 2,356 cache files: `put` 3.3 ms per file, the first `get` 6.7 ms per file, later `get`s 0.4 ms per file; plain uncompressed JSON was worse (16 ms per first read). Parsing costs about 1.1 ms per file (2,517 files in 2.7 s), so on this machine the disk cache only pays off from the third read of a blob. On Linux (CI, servers) file reads are fast.
  - **Pool cost:** two spawned workers need 3.6 s to report ready (importing pandas is about 2.6 s per process here). For pylint's 2,517 files in-process parsing takes 2.7 s, the pool 5.9 s with 2 workers and 5.8 s with 4. The pool is therefore slower on batches of this size; it is kept for big cold batches because it gives the hard per-file limit and survives parser crashes. Per-task IPC is cheap (500 round trips in 0.2 s).
- Known issues / limitations:
  - The time limit is soft outside the pool: a pathological file in a small batch, or anything inside a Celery prefork worker, runs to the end before it is dropped as `timeout`.
  - Name-set lineage (P1.1): a reused name can give a file the old file's versions in `cc_trend` (and its history in the E, O and D families).
  - Population issues owned elsewhere: celery's `t/` tests are ranked as source (`is_test_file` is P1.2's), pylint's `doc/data/messages` examples are ranked (filters are P1.2's, see P2.6), and `requests/packages/` vendoring before 2.16 is not caught by `VENDOR_DIRS` (P2.5).
  - `cc_trend` is 0 for most files (1,048 of 1,098 in pylint), since most files did not change complexity within a year.
  - Old first-parent date inversions (pre-2016, P1.5 fact c) can make an older `cc_trend` state slightly off; recent snapshots are unaffected.
  - SATD candidate lines are blamed even when the classifier rejects them (time only, results are unaffected).
