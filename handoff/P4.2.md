    - `path: str`
    - `before: tuple[int, Band, float]` and `after: tuple[int, Band, float]`: (priority 0..100, band, calibrated

    the file's model input row after the actions (float32 Series indexed by `FEATURE_INPUT_COLUMNS`, named
    `path`) and the changed raw features
  - `what_if(features: pd.DataFrame, path: str, actions: Sequence[str], bundle: Bundle) -> WhatIfResult`
  - `Bundle` is imported only under `TYPE_CHECKING`, so `import tdp_core.planning.whatif` does not load xgboost.

- Rules as implemented:
  1. Actions: a bare `str` raises `TypeError`; any name outside `WHATIF_ACTIONS` raises `ValueError` naming
     every unknown entry and listing the allowed names; actions are validated before the frame is read. The
     result is the distinct names in `WHATIF_ACTIONS` order (set semantics; `[]` means no change).
  2. Frame: `features.set_index("path")` when a `path` column exists (BuildResult and dataset shape), else the
     index is the path (AnalysisResult shape). Repeated paths, missing model input columns (count and the first
     five names), repeated model input columns, non-numeric values, and NaN or infinite values (including
     float64 values beyond the float32 range) raise `ValueError`. Extra columns and any column order are fine.
     A path without a row (also any path in an empty frame) raises `KeyError(f"no feature row for {path!r}")`.
  3. Targets from the file's old value `v`: `add_tests` sets has_test_file 1, test_importers 1 and
     test_cochange_rate to the float64 median over the OTHER files with test_importers > 0 (no target, value
     kept, when there is none); `split_longest_function` sets cc_max `max(CC_MAX_FLOOR, v/2)`, cog_max `v/2`,
     longest_function `v/2`, nesting_max `max(0, v-1)`; `remove_duplication` dup_ratio 0; `resolve_satd` the
     three SATD columns 0; `break_cycle` scc_size 1 and hidden_coupling 0. `pkg_test_ratio` and every E, O and D
     column are never touched.
  4. Never worsen: `new = max(v, t)` for `RAISED_COLUMNS`, `min(v, t)` otherwise, then cast to float32; a column
     whose float32 value does not change gets no entry.
  5. Percentiles: each changed column with a pct_ copy gets
     `pct = (count(other < new) + 0.5 * count(other == new) + 1) / n` over the other `n - 1` files (float32 of
     the float64 result), which equals pandas `rank(pct=True, method="average")`; every other entry of the row is
     copied bit for bit.
  6. Scoring: one `bundle.ranker.score` call on the `n` original rows plus the changed row; `before` = the
     file's priority among the `n` original scores, `after` = its priority with only its own score replaced
     (`priority_from_scores` both times); risks from one `bundle.calibrator.predict` call on the two scores.
  7. One debug log line per call; inputs are never modified; pure and thread safe.
- Deviations from the plan and why:
  - D1. The percentile uses `+ 1`, not the plan's `+ 0.5`. P2.7 rule 8 and `synthetic_dataset` define
    `pct_x = rank(pct=True, method="average")`; for one value among the other `n - 1` files that is
    `(count(o < v) + 0.5 * count(o == v) + 1) / n`. With `+ 0.5` every recomputed percentile would sit `0.5 / n`
    low, a value that did not move would still shift the model input, and the top file could never reach 1.0.
    Tests: every changed percentile equals pandas' rank bit for bit, and the stored synthetic percentiles follow
    the same rule for all 89 columns.
  - D2. Only CHANGED columns get a new percentile (as the P3.0 handoff advises). Recomputing untouched columns
    from float32 values could move ties against P2.7's ranking and nudge unconstrained inputs; this way a no-op
    is exactly a no-op.
  - D3. The never-worsen rule fixes a flaw in the plan: `cc_max = max(10, cc_max / 2)` RAISES cc_max for files
    below 10 (flagged in the P3.0 handoff), and splitting a function never adds complexity. One uniform rule
    means no action ever moves a feature the wrong way; it gives `cc_max = min(v, max(10, v / 2))` and keeps an
    out-of-range scc_size of 0 at 0.
  - D4. The add_tests median uses the OTHER files with test_importers > 0, consistent with "against the other
    files' values" (the file itself would pull the median towards its own rate). With no such file the rate is
    kept, because there is no reference value.
  - D5. Actions are a set: duplicates are ignored, order does not matter and `[]` is allowed. The five actions
    touch disjoint columns, so only a repeated split_longest_function could differ, and halving twice is not a
    meaningful UI request.
  - D6. Error types: unknown action `ValueError` (plan); bare string `TypeError`; missing path `KeyError` (like
    `make_plan`); repeated paths, missing or repeated model columns, non-numeric or non-finite values
    `ValueError` (like `Ranker.score`).
  - D7. Both frame shapes are accepted (the `make_plan` rule). Comparisons happen in float32, the precision the
    ranker sees.
  - D8. "Score all files" is one `n + 1` row ranker call. Per-row XGBoost margins do not depend on the batch, so
    this equals rescoring the whole modified frame (tested against a full rescore). `before` is recomputed with
    the given bundle, so it equals the stored analysis values when the bundle is the analysis's model version.
  - D9. `changed_features` lists raw features only, in `FEATURE_COLUMNS` order; values are float32 values
    widened to float, the same numbers `to_jsonable` stores in `file_results.features`. The pct_ copies of those
    columns are recomputed but not listed.
  - D10. Interface refinements: `before`/`after` are typed `tuple[int, Band, float]` (compatible with the plan's
    `tuple[int, str, float]`), `slots=True` is added, and the public additions `apply_actions`,
    `WhatIfResult.to_json`, `ACTION_COLUMNS`, `RAISED_COLUMNS` and `CC_MAX_FLOOR` serve tests, P5.4 and a possible
    after-state explanation.
  - D11. `Bundle` is imported only under `TYPE_CHECKING`, so importing the module stays free of xgboost (about
    4 s on this laptop); P4.1's modules are free of it too. A subprocess test guards this.
  - D12. The plan's soft acceptance check is strict here. The dev ranker is exactly monotone in every action
    column and its pct_ copy (`DEV_MONOTONE_CONSTRAINTS`), and every action only moves columns in the improving
    direction, so score, priority and risk can never rise with the dev bundle. The tests assert that for all
    200 files of a query and six action sets, and for every one of the 32 action subsets on the top files.
  - D13. Fixtures live in the test module (`tests/model/conftest.py` is not visible from `tests/planning`). The
    dev bundle is built once per module (about 1 s).
  - D14. Values beyond the float32 range are rejected as infinite instead of silently becoming `inf` (the cast
    warning is suppressed and the `ValueError` names the column).
  - The branch name comes from the build harness, not the plan's `step/P4.2-whatif`.

- Known issues / limitations:
  - The simulation is ceteris paribus: other files keep their features, percentiles and scores (their
    percentiles would move by at most `1 / n`), and the other members of a broken cycle keep their scc_size.
  - A real model without monotone constraints can predict a worse state after an action; the result reports it
    as it is.
  - risk_low, risk_high, cost, reasons and debt types are not recomputed for the after state.
  - The action rules are fixed heuristics (one split halves the worst function, one added test file gives one
    test importer); they do not inspect the code.
