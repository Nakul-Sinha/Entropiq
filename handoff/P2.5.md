- Deviations from the plan and why:
  1. **Cursor pagination instead of `page=N`.** The crawl follows the `Link: rel="next"` URL. GitHub answers 422 ("Pagination with the page parameter is not supported for large datasets") from `page=100` on, so `page=N` cannot fetch repos with more than about 9,900 issues and pull requests (pytest, fastapi, pip, aiohttp, pylint, poetry, celery, DRF). The first request sorts by `created asc` for a stable crawl. A next link that leaves the API host raises `GitHubError`, and redirects (renamed repos go to `/repositories/<id>/...`) are followed only on the same host, so the token never goes anywhere else.
  2. **Not-a-bug labels never count, and they veto the issue.** The plan's label regex also matches triage verdicts: requests 'Question/Not a bug' (71 issues, next to 130 real 'Bug' issues), celery 'Status: Not a Bug', black 'R: not a bug', pip 'resolution: not a bug'. `is_not_bug_label` (`(not|non|no)[\s_-]*(a[\s_-]+)?bug`) catches them, and an issue with both a bug label and a not-a-bug label is not a bug.
  3. **Cache behaviour.** `read_issues` recomputes `is_bug` from the labels, so a label-rule change never needs a refetch. The cache is written atomically (`.tmp` then `os.replace`) and only after a complete crawl (`max_pages` results are never cached). An unreadable cache is refetched. HTTP 410 (issues disabled) gives an empty table.
  4. **Networking the plan leaves open.** Transport, sleep and clock are injectable, so all default tests are offline. Network errors, 5xx answers and truncated or non-list bodies are retried up to 5 times with 5, 10, 20, 40, 80 s backoff (the laptop's hotspot drops). A used-up primary rate limit sleeps until `x-ratelimit-reset` (at most 3 waits per request), a secondary limit honours `retry-after` (60 s default). 401, 404, 422 and refused redirects raise `GitHubError` with the status and GitHub's message, never the token.
  5. **Issue references.** `#N` counts unless a word character or `&` comes before it (HTML entities like `&#39;`, colours like `#123abc` are skipped). `GH-N` also counts, and `fixes/closes/resolves #N` is covered by `#N`. References into other repositories (`owner/name#N`, issue URLs) are ignored. With the new optional `repo="owner/name"`, same-repository issue URLs and same-repository `owner/name#N` count too. The planner's plan ignored `owner/name#N` even for the repo itself, but this is additive and the default (`repo=None`) keeps the plan's behaviour.
  6. **Reverts.** `Revert "X"` claims nothing from X (its subject becomes empty, its own body still counts, for example "X caused a regression"), and a revert of a revert or `Reapply "X"` claims X. "This reverts commit <sha>" lines are dropped. Without this, 51 quoted reverts of fixes in the 23 mirrors would be keyword fixes, and SZZ would blame a fix's own lines as bug-inducing.
  7. **Subject first.** A subject with a fix keyword or a non-fix phrase decides. The body only matters when the subject is neutral. For one-line messages this is exactly the plan's rule. It keeps squash-merged fixes whose body lists "fix tests" or "fix typo" (74 such commits in the 23 mirrors).
  8. **Wider non-fix veto.** It allows up to two filler words ("a", "the", "some", "minor", "failing", "flaky", "broken", "couple of", ...) and the -ing form, and adds the targets docstrings, grammar, wording, mypy, flake8, pre-commit, typing (but not `typing.`), type hints, examples and broken/dead links. All of the plan's targets are kept. Words that are real code topics in some repos (comments, links, annotations, warnings, version) were left out on purpose (scrapy fixes link extractors, black fixes comment handling).
  9. **Declared commit types.** Conventional types `docs/doc/ci/test/tests/chore/style/build/refactor/feat` (optional scope, `!`) and non-fix gitmoji (memo, pencil, art, check mark, construction worker, arrow up, globe, rotating light, recycle, sparkles, wrench, bookmark, as emoji or `:name:`) veto the keyword source. The bug, ambulance and adhesive bandage gitmoji count as a fix keyword (fastapi has 43 bug-gitmoji fixes without a keyword). The issue source ignores declared types (plan rule 2).
  10. **Eligibility.** A change counts only when it is not binary and has `added + deleted > 0` (pure renames and mode changes do not count). The pre-rename path counts too. `default_is_source` also drops vendored paths (`VENDOR_DIRS`), so detection, SZZ and ranking use one population.
  11. Kept the plan's rule that a commit referencing only non-bug issues may still be a keyword fix ("Fixes #9" with #9 a feature request is a keyword fix). In the measurement this caused 5 of 22 false positives (see the candidate improvements under Known issues). A veto by label would depend on per-repo label names, and most requests issues have no label at all.
  12. **Evaluation tools.** The logic lives in `ml/tdp_ml/tools/{sample_bugfix,score_bugfix}.py` as the plan says, reachable as `tdp-ml` plug-in commands (15.4). Sampling is stratified by detector source over eligible commits (ineligible commits are non-fixes by construction), blind (the prediction is in a separate `.key.csv`), seeded, shuffled (any prefix of rows is a valid subsample), and never overwrites a labelled CSV without `--force`. It requires `n >=` the number of non-empty strata, so the key knows every stratum's size. Scoring uses design weights `N_s / labelled_s`, so the estimates hold for the whole population, and `--bugfix` re-scores another detector on the same labels.
  13. Token: `GITHUB_TOKEN` first, else `gh auth token` (15.6), looked up only when the issues cache is missing. Issues are cached in `$TDP_DATA_DIR/issues/<slug>.parquet`, and evaluation files go to `$TDP_RESULTS_DIR/bugfix_eval/` (not committed).

- Measured results (Windows laptop, other slots busy at the same time):
  - **Issue crawl, psf/requests:** 73 pages (about 7,200 issues and pull requests), **4,181 issues, 130 bug issues**, 249.5 s with a token over the hotspot (about 30 items per second; the planner measured about 2 minutes on a quiet link). Cached at `$TDP_DATA_DIR/issues/psf__requests.parquet` (96 KB). `read_issues` 0.1 s.
  - **Classification, psf/requests:** 4,884 commits, 2,392 eligible; **issue 38, keyword 388, none 1,966 eligible** (plus 2,492 ineligible). Without issues: keyword 409. `classify_bugfix` takes 0.03 to 0.33 s (busy machine), `mine_history` 1.4 to 4.5 s. Synthetic 50,000 commits x 4 changes: about 2 s.
  - **Hand-labelled sample** (`$TDP_RESULTS_DIR/bugfix_eval/psf__requests.sample.csv`, seed 42, all 200 rows labelled in row order before the key was opened). **Labels were assigned by the building agent, not by a human.** Rule: 1 when the commit repairs wrong behaviour of the project's own non-test code (crash, wrong result, regression, hang, leak, security hole, broken support for a supported Python version or dependency); 0 for features, refactors, docs, typos, tests, CI, packaging, version bumps and vendored dependency updates. 15 rows are marked unsure in their note (4 more carry other notes). Diffs and issue titles were checked for unclear rows.

    | stratum | population | labelled | bug fixes | rate | Wilson 95% |
    |---|---|---|---|---|---|
    | issue | 38 | 38 | 35 | 0.921 | 0.792 to 0.973 |
    | keyword | 388 | 82 | 63 | 0.768 | 0.666 to 0.846 |
    | none | 1,966 | 80 | 18 | 0.225 | 0.147 to 0.328 |

    **Weighted precision 0.782, recall 0.430, F1 0.554** (estimated 333 true fixes among 426 predicted, 775 bug fixes among the 2,392 eligible commits). Precision is good. Recall is low because requests' messages often describe the change without any keyword, and most of its bug issues carry no label.
  - **False positives** (22 of 120 predicted rows): setup.py or packaging fixes (4); "fix" aimed at text, docs config, flake8 or a type annotation outside the veto list (4); "fixes #N" closing a feature, docs or design issue without a bug label (5); vendored urllib3 updates under `requests/packages/` (3, see Known issues); follow-ups such as import moves during unvendoring and "Moved fix for #747" (3); a stray "fix" or "regression" in the body of a non-fix (2); an issue labelled both "Feature Request" and "Bug" (1).
  - **False negatives** (18 of 80 rows in `none`): almost all state the repaired behaviour without a keyword ("Default proxy scheme to http.", "Always percent-encode location headers.", "may have multiple encoding values", "Don't let proxy_bypass bring you down."). 3 reference an issue or pull request without a bug label.
  - **Against the plan's unrefined rule** (plan keyword and veto regexes, plan label regex, `#N`/`GH-N` on the raw message): it flags 454 eligible commits instead of 426. None of the 28 extra commits fell in the sample (re-scoring with `--bugfix` gives identical numbers). By subject, 27 of the 28 are non-fixes (reverts of fixes, typo, test, flake8 and doc-link fixes), so the refinements raise precision from about 0.735 to 0.782 at the same recall on this repo.
- Known issues / limitations:
  - **Vendored code under `requests/packages/` (before 2.16) is not caught by `VENDOR_DIRS`** (which has `_vendor`, `vendor`, `third_party`, ... but not `packages`), so vendored urllib3/chardet updates count as source commits, and P2.7 would rank those files too. Fixing it means adding a rule to `tdp_core.parsing.filters` (owned by P1.2). One option is to treat `<pkg>/packages/<name>/` as vendored when `<name>` is a known third-party project. I did not change it here.
  - Keyword recall is limited (0.43 on requests). Candidate improvements, each measured on a fresh sample from another repo before adoption (they were seen on this evaluation sample, so adopting them here would overstate precision): ignore "fixes #N" when #N carries a feature or documentation label; veto subjects like "Update <dependency> to <version or sha>"; treat setup.py-only commits as packaging.
  - Pull requests are excluded from the issues table (plan rule 1), so "Fixes #N" pointing at a pull request never links, even when that pull request has a bug label.
  - A repo that moved from another tracker can have old `#N` references that collide with GitHub numbers. I did not see this in requests.
  - Commits cherry-picked between branches can appear twice in `--no-merges` history with the same message, so both copies are classified.
  - Labels and timings come from one repository and one labeller (the agent).
