## Deviations from the plan and why
1. Constraint names follow Postgres's own default names through a naming convention, so the migration, the models and
   the plan's raw DDL produce identical schemas and later migrations can address constraints by name.
2. More repositories than the plan lists (repositories, model versions, artifacts, plans, advice, feedback,
   `AnalysisRepo.get/requeue/list_for_repository`, `FileResultRepo.list_all`), because section 2.6 lets P5.3 and P5.4
   only import from `db/*`. Every state method takes an explicit `analysis_id`.
3. `AnalysisRepo.create` returns `(analysis, created)` using `INSERT ... ON CONFLICT DO NOTHING`, so POST /analyses is
   race free.
4. State machine: `set_running` from queued or running (keeps `started_at`, stage and progress; a redelivered task can
   call it again), progress while queued or running, `set_succeeded` only from running, `set_failed` from queued or
   running, `requeue` only from failed (also deletes the old results, artifacts and plans). Each returns False when the
   row was not in an allowed state.
5. The cursor encodes `(sort, order, value, id)` instead of only `(priority, id)` because the API sorts by four keys; for
   the default sort it is still `(priority, id)`. Ties break by id ascending in both orders (ids follow path order,
   since rows are stored in `AnalysisResult.files` order). `sort=path` uses `COLLATE "C"` (code point order like Python;
   the postgres image's default en_US collation differs). `sort=cost` uses `cost_high`.
6. `bulk_insert` replaces an analysis's rows by default (idempotent retries under acks_late), validates rows before the
   COPY and checks that the analysis exists. It issues a SELECT through the session first, which makes SQLAlchemy's
   asyncpg adapter open the transaction, so the raw COPY is part of the caller's transaction.
7. `rows_from_result` in `db/rows.py` pins the JSON shapes of file_results so the writer and the reader agree.
8. Strict JSON at the engine (`json_dumps`: `to_jsonable`, no NaN, no NUL, no lone surrogates) because JSONB rejects them;
   bad data fails with ValueError before any SQL instead of failing mid-COPY.
9. Plan budgets are compared as REAL (`CAST(:budget AS REAL)`): asyncpg binds Python floats as float8 and a REAL 0.1
   never equals float8 0.1.
10. Migrations always run on psycopg (sync), through programmatic helpers, inside one transaction holding a Postgres
    advisory lock (concurrent migrators run one after the other). A thread lock serialises the helpers inside one process
    because Alembic's `context`/`op` proxies are process globals.
11. New optional setting `DATABASE_SCHEMA` plus `schema` parameters and `db/testing.py`, so the integration tests of the
    platform, worker and API (one CI database, one pytest run) stay isolated in temporary schemas.
12. Settings: `allowed_git_hosts` is an immutable tuple parsed from a comma list (the plan says list); secrets are
    `SecretStr`; URLs are hidden from repr; empty values are ignored; settings are frozen; `repo_cache_dir` and `model_dir`
    fall back to `tdp_core.paths` (section 15.2 shared folders), which equals `.env.example` when the TDP_* variables are unset.
13. `PostgresStaticCache` stays in `repos.py` as the plan says; unstorable parses are skipped and undecodable rows count as
    misses (with a warning).
14. Extra modules under `db/` (pagination, rows, migrate, testing) and the `py.typed` marker; section 2.6 gives `db/*` to this step.
15. No edits to ci.yml (15.6: CI already has the Postgres 16 service and TEST_DATABASE_URL), `.env.example`, Makefile or
    pyproject files; MAX_REPO_KB, ADVISOR_ENABLED and DATABASE_SCHEMA are documented in `settings.py` and here.

`compare_metadata`, run two migrating processes at once, and exercise every repository.

## Known issues / limitations
- The Postgres behaviour is verified only in CI (no local database on the development machine).
- `commit_sha` and `blob_sha` are `CHAR(40)`: SHA-1 repositories only.
- `alembic.ini` and `alembic/` live outside the `tdp_platform` wheel; migrations need the source tree (workspace or editable install).
- `bulk_insert` raises asyncpg's own exceptions for COPY errors (only reachable with `replace=False` duplicates).
- With mypy 2.x and pydantic's dataclass transform, `PlatformSettings(_env_file=None)` is flagged as an unknown keyword;
  tests build settings through a `**kwargs: Any` helper.

## Notes for dependent steps
- **P5.3 worker:** create one engine per process with `create_async_db_engine(s.database_url, schema=s.database_schema,
  null_pool=True)`; it is safe across repeated `asyncio.run()` calls (a pooled engine is bound to one loop). Call
  `ModelVersionRepo.ensure(bundle.version, bundle.metadata.get("metrics", {}))` before creating analyses. Call
  `set_running` before `set_succeeded` (succeeded only from running; False means another actor changed the state: roll
  back). Persist in ONE transaction: `FileResultRepo.bulk_insert(aid, rows_from_result(result, shap_by_feature=...))`,
  `ArtifactRepo.put(aid, "graph", result.graph)`, `ArtifactRepo.put(aid, "treemap", tree)`,
  `PlanRepo.put(aid, analysis.budget_hours, result.plan)`, `AnalysisRepo.set_succeeded(aid, summary, result.stats)`.
  On failure `set_failed(<user-safe message>)` in its own transaction. Progress updates should use their own short
  transactions (`async with factory.begin() as s`). Advice: `AdviceRepo.create_queued`, then
  `set_ready(advice.model_dump(mode="json"))` or `set_failed`. Static cache:
  `PostgresStaticCache.from_url(s.database_url, schema=s.database_schema)` used in the parent process only; it returns
  the `FileSyntax` as stored, so when the same blob sits at another path replace `path` with `dataclasses.replace`.
  Tests: `temporary_schema(TEST_DATABASE_URL, prefix="tdp_worker_test")`, set `DATABASE_SCHEMA` and call
  `get_settings.cache_clear()`; empty tables between tests with `truncate_all`.
- **P5.4 API:** lifespan `engine = create_async_db_engine(s.database_url, schema=s.database_schema)`; a dependency
  yields `make_session_factory(engine)()` and commits. POST /analyses: `RepositoryRepo.get_or_create(url=ref.canonical_url,
  host=..., owner=..., name=...)`, `ModelVersionRepo.ensure(<production version>)`, `AnalysisRepo.find(...)` (reused) or
  `create(...)` returning `(analysis, created)`; COMMIT before calling `start_analysis`; `reused = not created`; a failed
  analysis can be retried with `requeue`. GET analysis: `AnalysisRepo.get` (`analysis.repository.url` is loaded;
  `commit_sha` is the 40 character string). Files: `list_ranked(sort, order, bands, debt_type, path_prefix, limit,
  cursor)` gives `{items, next_cursor, total}`; map `InvalidCursorError` and `ValueError` to 400; items carry summary
  columns only (touching the JSON columns raises). Detail: `FileResultRepo.get(file_id, analysis_id=id)`; decode `extra`
  with `from_jsonable(FileExtra, row.extra)`; `reasons` JSON is `{"reasons": [...], "mitigations": [...]}`; `shap` is
  `{"by_family", "by_feature"}`; `features` holds all `FEATURE_INPUT_COLUMNS` (JSONB does not keep key order: rebuild
  frames in `FEATURE_INPUT_COLUMNS` order). Plan: `PlanRepo.get/put` (budgets compared as REAL); recompute from
  `list_all`. Graph and treemap: `ArtifactRepo.get`. Feedback: `FeedbackRepo.create`. Trend:
  `list_for_repository(repo_id, status="succeeded")` reading `summary`. `/readyz`: `await session.execute(text("SELECT 1"))`.
  Service-only settings: subclass `PlatformSettings` in `tdp_api`.
- **P2.7 / P5.2:** `PostgresStaticCache` matches the `StaticCache` protocol (`get`/`put`), keyed by blob sha plus
  `EXTRACTOR_VERSION`.
- **P7.4:** run migrations with `uv run alembic -c packages/platform/alembic.ini upgrade head` (or
  `python -c "from tdp_platform.db.migrate import upgrade; upgrade()"`) with `DATABASE_URL` set (an asyncpg URL is fine,
  migrations switch to psycopg). Images must ship `packages/platform` (alembic files are not in the wheel). Concurrent
  upgrades are serialised by the advisory lock.
- **P7.6:** no logging or metrics modules were created; add them under `tdp_platform` without touching `db/`.
