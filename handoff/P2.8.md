- Deviations from the plan and why:
  - D1. Commands are a plug-in module `tdp_ml/commands/pipeline.py` (15.4), not `cli.py`.
  - D2. The manifest was built on the laptop and copied to the box; every stage mines and selects at the manifest sha, never `HEAD`. The box mirrors were 1 to 14 days ahead for 8 repositories, with the laptop heads on their first-parent chains (measured), so snapshot and window-end states are identical; `snapshots` checks that every snapshot and window-end sha is an ancestor of the manifest sha.
  - D3. All mining uses the `.mailmap` of the mined commit (`mine_at`). Features at T see only T's mailmap (otherwise ownership features and commit identities leak later `.mailmap` edits and the leakage check fails); the full history is pinned to the manifest sha's mailmap so laptop and box mine identical tables.
  - D4. Two bug-fix tables per repository: keyword-only for the D features (train and serve parity with P5.2; an issue label can be added after T), issue-aware for labels (P2.5 recommendation). The 5 repositories with 5,000 or more GitHub issues (poetry, celery, pytest, pip, pylint) are not crawled (`issues: false`): their labels use keyword detection and their bug-issue criterion is waived.
  - D5. SZZ traces the label-window fixes of each kept snapshot (chosen by reachable sets, not author time) plus the newest `inference_szz_max_fixes` (300) prior keyword fixes of each kept snapshot (keeps `prior_latent_bugs` equal to inference). The budget of 1,500 unique fixes per repository is enforced by dropping the oldest kept snapshots until the union fits; in the real run no snapshot had to be dropped (largest: aiohttp, 657 label and 782 feature fixes). This supersedes 15.6's "only window fixes".
  - D6. Criteria: `min_source_files` is 20, not 80 (80 keeps 12 of the 23 mirrored repositories, below 15.6's floor of 15 and the acceptance's 20). Thresholds are inclusive; source files = feature rows of the newest kept snapshot; "a commit in the last 12 months" is measured against the manifest's `created_at`. `dataset` evaluates the criteria from exact counts, so there is no separate criteria command, and failing repositories are reported in `dataset.json`, not deleted.
  - D7. The 8 newest snapshots of the schedule per repository (`labels.yaml`), with their original schedule indexes.
  - D8. Lineage is stored per snapshot so `labels` gets exactly `BuildResult.lineage` without rebuilding features.
  - D9. `qid = repo id * 100 + snapshot index` (int64), stable across re-runs; ids are fixed in `repos.yaml` (1-based positions in the plan's 30-candidate list).
  - D10. `--jobs` = repositories in parallel (spawned processes), `--threads` = SZZ git threads; `build_features` always runs with `jobs=1` (no nested pools).
  - D11. `check-leakage` clones with `--no-local --no-checkout`, checks out a `snapshot` branch at the sha and deletes every other ref, then rebuilds with keyword detection and SZZ for the newest 300 prior fixes inside the clone, without caches, and compares at rtol = atol = 1e-6. It ran on the box where the features were built.
  - D12. Empty queries are left out of the dataset (none occurred); nothing else is filtered.
  - D13. Bug-fix detector precision and recall come from P2.5's hand-labelled psf/requests sample: weighted precision 0.782, recall 0.430, F1 0.554 (200 commits). No new manual sample was labelled.
  - D14. Training mines all history (plan note 3) while inference mines 3 years: a known train and serve skew for P3.x, not changed here.
  - The planned separate test files for config, layout, history and dataset helpers are combined in `test_pipeline_helpers.py`.
