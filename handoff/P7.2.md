- Deviations from the plan and why:
  - D1. Section 3.6 lists `to_markdown`, `to_json` and `to_sarif` under `tdp_core.report`, but section 15.4 (which overrides it) keeps `report/__init__.py` docstring only. Callers import from `tdp_core.report.markdown`, `.jsonout` and `.sarif`.
  - D2. Shared helpers live in an extra module, `report/common.py`, inside the owned subpackage. `summarize` returns exactly the `Analysis.summary` shape of section 3.7 with the same numbers as the worker's `build_summary`: `critical_hours` is the sum of `extras[path].cost.hours` over Critical files (missing or non-finite cost adds 0), rounded to 2 decimals; each histogram bucket is `min(max(priority, 0) // 10, 9)`; every `DEBT_TYPES` key appears, zeros included, and unknown names follow in sorted order. Each debt type counts files, so a name repeated within one file counts once.
  - D3. Additions on top of the plan's interface: `plan_to_markdown(plan)` for `tdp plan`; `to_json_dict`, plus a keyword only `indent` on `to_json`; `top=None` lists every file. A full Markdown report is `to_markdown(result) + "\n" + plan_to_markdown(result.plan)`.
  - D4. `to_markdown` sorts files itself (priority descending, then path). `only_paths` selects exact repo-relative POSIX paths (meant for the files a PR changes); paths that are not ranked are ignored. A bare `str` for `only_paths` raises `TypeError`, and `top < 1` raises `ValueError`. Layout: the heading `## Technical debt report`; a commit, model and time line (UTC to the minute); a summary sentence, with critical hours when there are any; the table from the PR comment example in docs/TDP-2 section 11.2 (`File | Priority | Risk (12 mo) | Top reason`, priority shown as `95 Critical`, risk as a whole percentage, `-` when a file has no reason); a `Showing the top N of M files.` footer when rows are cut. The output ends with exactly one newline and has no carriage returns. The writer adds no hidden marker (P7.3 adds `<!-- tdp-report -->`).
  - D5. Markdown safety for untrusted paths: paths go into code spans with a fence longer than any backtick run inside, and pipes are escaped inside tables. Free text is backslash escaped. Non-printable characters (control, bidi, zero width, NBSP, lone surrogates) are written as visible escapes. Tests use markdown-it-py (installed through rich) as a GFM oracle, plus hypothesis property tests.
  - D6. JSON layout: keys `format`, `format_version`, `tool` (`name`, `version`), `sha`, `analyzed_at` (ISO 8601 ending in `Z`), `model_version`, `extractor_version`, `summary`, `files`, `extras`, `graph`, `plan`, `stats`. `files` keeps the input order; each entry is the `FileScore` plus a `features` object holding its row of `result.features` (float32 written in shortest form). `extras` are sorted by path. NaN and infinities become `null`. The text is strict ASCII JSON ending in a newline. `format_version` changes only when an existing key changes meaning or is removed. When every number is finite, `from_jsonable(AnalysisResult, json.loads(text))` rebuilds every field except `features` (an empty DataFrame).
  - D7. SARIF `$schema` is the OASIS errata01 URL, which is the id of the committed official schema. `helpUri` is omitted (optional in the plan). Rules also carry `name`, `fullDescription`, `defaultConfiguration.level`, `help.text` and `tags`.
  - D8. The plan says uri = path. The writer percent-encodes the path into a valid RFC 3986 relative reference, which is identical for ordinary paths (a space becomes `%20`, a leading `/` becomes `%2F`). CodeQL does the same and upload-sarif decodes it. `uriBaseId` is `%SRCROOT%`. No fingerprints are written; upload-sarif computes them.
  - D9. `min_band` accepts only `"Critical"` or `"High"`, because only those two rules exist; anything else raises `ValueError`. Both rules are always listed. `rank` is the priority clamped to 0..100 as a float. Each result's `properties` hold `priority`, `band`, `risk`, `risk_low`, `risk_high` (null when not finite) and `debt_types`; the run's `properties` hold `sha`, `analyzed_at`, `model_version` and `extractor_version`. The message reads "<Band> maintenance priority: P of 100. Estimated chance that a bug in its current code is fixed within 12 months: R% (L% to H%). Top reasons: a; b; c."
  - D10. `region.startLine` is the start of the most complex function: highest cyclomatic complexity, then highest cognitive complexity, then earliest start line, then smallest name. A file without functions gives 1, and a start line below 1 is raised to 1.
  - D11. All three writers raise `ValueError` for a naive `analyzed_at`.

- Known issues / limitations:
  1. A JSON document holding `null` for a float field (from a NaN or infinity) cannot be rebuilt with `from_jsonable` (it raises `TypeError`, tested). Real `analyze()` output is finite.
  2. Markdown free text (reason texts, and plan reasons that contain paths) does not neutralise GitHub @mentions, #references or bare URL autolinks. Paths in table cells sit in code spans and are safe.
  3. One SARIF result per file; the region points at the most complex function, not a precise defect.
  4. The GFM oracle tests skip if markdown-it-py is missing.
  5. The summary logic exists twice: `report.common.summarize` and the worker's `build_summary` (P5.3). Both give the same output for valid results.
