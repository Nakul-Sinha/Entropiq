- Deviations from the plan and why:
  1. **Deletions in `path_lineage` are inferred, because `FILE_CHANGES_SCHEMA` has no change-type column.** A deletion is `added=0, deleted=N`, which looks exactly like a change that only removes lines, and creating or deleting an empty file is `0 0` either way. `path_lineage` tracks a running line count per path (carried through renames) and treats a text change with `added == 0`, `deleted > 0` that brings the count to exactly 0 as a deletion. The count becomes unknown, so no deletion is inferred, after a binary change or when it would go negative (files that predate a `since` window). Results: deleting an empty or binary file is not detected (the path stays in the result), and a text file emptied to 0 lines counts as deleted (it is missing from the result). **Proposed contract fix (not applied, contracts are frozen for this step):** add `("change_type", pa.string())` (`A`/`M`/`D`/`R`/`T`) to `FILE_CHANGES_SCHEMA`. `mine_history` could fill it from the same `git log` run by adding `--raw`, and `path_lineage` would then be exact.
  2. Extra `run_git` hardening on top of the plan: inherited `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_COMMON_DIR`, `GIT_NAMESPACE`, `GIT_PREFIX`, `GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_COUNT`/`KEY_n`/`VALUE_n`, `GIT_EXTERNAL_DIFF` and `GIT_DIFF_OPTS` are removed, so running inside a git hook (pre-commit) cannot redirect git to another repository or inject config. `user:token@` in URLs is redacted from exception messages, `stderr` and `cmd`. stdin is closed when `input` is None. With `allow_file_protocol=True`, `GIT_ALLOW_PROTOCOL` is removed rather than set, as the plan says.
  3. `ensure_mirror` fetches with `git --git-dir=<dest> fetch --prune --tags origin` instead of `git -C dest ...`. Without `--git-dir`, a `dest` that exists but is not a repository (for example a broken `data/mirrors/x.git` inside this checkout) makes git walk up and fetch/prune the enclosing repository. I reproduced this; `test_non_repo_dest_inside_a_checkout_is_left_alone` covers it. The clone passes `--` before the URL so a URL can never be read as an option.
  4. `mine_history` pins output-affecting config: `-c log.showRoot=true` (otherwise a global `log.showRoot=false` hides the root commit's files), `-c log.showSignature=false`, `-c diff.algorithm=myers` (line counts must not depend on the user's diff algorithm), plus `--encoding=UTF-8 --no-color --end-of-options <rev> --`. Revisions starting with `-` raise `ValueError`; negative `max_commits` raises `ValueError`.
  5. `list_files` also keeps legacy mode `100664` (a regular file mode found in old histories) besides `100644`/`100755`; symlinks (`120000`) and submodules (`160000`) are dropped.
  6. `read_blobs` raises `GitError` for missing, ambiguous or non-blob objects instead of silently skipping them, dedupes its input, and returns `{}` for empty input without starting git.
  7. Added `parse_git_log` and `check_rev` as public helpers (used by tests; P5.5 may reuse `check_rev` for user-supplied refs).

- Measured results (Windows 11 laptop, git 2.49):
  - `psf/requests` (4,883 non-merge commits, 8,036 file changes, 77 renames, 48 binary changes, 3 bulk commits, 1,612 merges skipped): `ensure_mirror` clone 42.1 s, re-fetch 5.2 s, **`mine_history` 1.38 s**, `make_snapshots` gives 28 snapshots, `path_lineage` 0.02 s, `list_files` + `read_blobs` of the last snapshot (130 files, 4.6 MB) 0.25 s.
  - Lineage on `psf/requests`: 504 of 3,119 snapshot files have rename history. At HEAD, 66 of 272 real deletions are not detected (merges and cherry-picks make the summed line counts drift; 15 binary, 8 empty files, 43 drifted text files). The effect is extra keys for paths that no longer exist. No live file at HEAD was wrongly dropped.
  - Across all 28 snapshots, 5 of 3,119 files in a snapshot tree are missing from the lineage. All 5 come from the author-time issue below (the snapshot tree contains commits authored after T), none from the deletion heuristic.
  - Test run: 49 mining tests in about 50 s, 72 tests overall in about 45 s (git process start-up dominates on Windows).
- Parsing edge cases found:
  - Layout under `-z`: each record is `\x1e<fields>\x1f<%B>\x1f` then a NUL; only if the commit changed files does a `\n` follow, then NUL-terminated numstat entries. Empty commits have no `\n`.
  - Rename entries are three NUL-separated tokens: `added\tdeleted\t` (empty path), old path, new path. Binary uses `-\t-`, also for renames.
  - Paths are verbatim under `-z` (spaces, tabs, newlines, unicode). Bytes that are not UTF-8 become U+FFFD; `list_files` decodes the same way, so both modules agree on such paths.
  - `\x1e` or `\x1f` inside a commit message is tolerated: a record only starts at `\x1e` followed by a full sha (40 or 64 hex) and `\x1f`, and the message ends at the first `\x1f` followed by NUL (messages cannot contain NUL).
  - Deleting a binary file shows as `-\t-\tpath`, the same as modifying it.
  - Submodule pointer changes appear in numstat as a normal 1-line change of the submodule path.
  - `--since` filters on the **committer** date, not the author date (git behaviour). The table is still sorted by author time.
  - With `since` or `max_commits`, `parents` can reference commits that are not in the table.
- Known issues / limitations:
  - The lineage deletion heuristic (deviation 1).
  - Lineage is a set of names, so it cannot express "history before the delete is dropped" when the same name is reused: a consumer that filters `file_changes` by `path in lineage` still sees pre-deletion commits of a recreated path with the same name. Only names that existed solely before the deletion are dropped.
  - **Snapshot leakage (plan-level, implemented as specified):** the snapshot sha is "the last commit with `author_time <= T`", but rebased or cherry-picked commits keep their old author date, so that commit's tree can already contain work authored after T. On `psf/requests`, snapshot 12 (T = 2018-02-05) has 89 ancestors authored after T (up to 125 days later) and snapshot 17 has 1; the other 26 are clean. It cannot be fixed inside P1.1's contracts: `COMMITS_SCHEMA` has no committer time, merges are excluded so `parents` cannot rebuild ancestry, and `make_snapshots` gets no repository. Options for the coordinator: add `committer_time` to `COMMITS_SCHEMA` and pick the sha by committer time on the first-parent chain, or have P2.8 drop or repair snapshots whose tree holds commits authored after T (check with `git log --format=%at <sha>`).
  - On Windows, cloning into a very deep directory fails with "Filename too long" (git pack paths exceed 260 characters). Keep mirror paths short there, or set `core.longpaths=true`.
  - `ensure_mirror` does not check that an existing mirror's `origin` URL matches `url`, and it uses `run_git`'s default 600 s timeout for clones.
  - `run_git` does not isolate the global git config (credential helpers and `url.insteadOf` keep working); the options that would change parsed output are pinned per call instead.
  - A repository with no commits makes `mine_history(..., "HEAD")` raise `GitError`.
