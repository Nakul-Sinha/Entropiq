  - `class Explainer` (`__slots__`):
    - `__init__(self, bundle: Bundle) -> None`: validates `bundle.reasons` (`ValueError` if incomplete or
      invalid), keeps a deep copy, builds `shap.TreeExplainer(bundle.ranker.booster)` (shap and xgboost imported
      lazily here).
    - `expected_value -> float` (property): TreeSHAP bias read from XGBoost's own contribution bias column.
    - `__repr__`: `Explainer(version='dev-...', expected_value=0.0856508)`.
    - `shap_values(self, X: pd.DataFrame) -> npt.NDArray[np.float64]`: shape `(len(X), 89)`; same column check
      and message as `Ranker.score`; float32 cast, NaN is missing, index ignored, empty frame gives `(0, 89)`;
      always every boosting round (`tree_limit=-1`).
    - `explain(self, X: pd.DataFrame, *, baseline: Baseline = "repo", max_reasons: int = MAX_REASONS) ->
      list[Explanation]`: one explanation per row, in row order; `X` must be one repository snapshot; NaN or
      infinite values, `max_reasons < 0`, an unknown baseline or wrong columns give `ValueError`; empty gives `[]`.
  - `load_templates(path: Path | None = None) -> dict[str, Any]` (None reads the packaged file).
  - `validate_templates(templates: Mapping[str, Any]) -> None` (`ValueError` naming feature and key).
  - `render_text(templates: Mapping[str, Any], feature: str, kind: Literal["template", "mitigation"], value:
    float, percentile: float) -> str`
  - `family_totals(phi_row: npt.ArrayLike) -> dict[str, float]`
  - `feature_totals(phi_row: npt.ArrayLike) -> dict[str, float]`
  - `render_reasons(row: pd.Series, phi_row: npt.ArrayLike, templates: Mapping[str, Any], max_reasons: int =
    MAX_REASONS) -> tuple[tuple[Reason, ...], tuple[Reason, ...]]`
  - `assign_debt_types(row: pd.Series, totals: Mapping[str, float]) -> tuple[str, ...]`

- Rules as implemented:
  - Reasons: families sorted by total (ties in `FAMILY_ORDER`), kept while the total is positive and strictly
    above 5% of `sum(|phi|)`, at most `max_reasons`. Within a family the feature with the largest
    `phi[x] + phi[pct_x]` wins (ties: earlier in `FEATURE_FAMILIES`). `Reason.shap` is the family total.
  - Mitigation: the family with the smallest total if it is negative and `-total` is strictly above 25% of the
    sum of positive totals (any negative family when none is positive); its most negative feature is reported.
    At most one, independent of `max_reasons`. All-zero SHAP values give no reasons and no mitigation.
  - `Reason.value` is the float32 value the model saw, written as its shortest decimal (0.1 stays 0.1).
    `Reason.percentile` is `100 * pct_x` rounded to 2 decimals and clipped to 0..100; binary features give 100
    when the value is 1 and 0 otherwise.
  - Text: the first `exact` pair matching the value, else the template or mitigation sentence; `{adj}` is the
    first adjective with threshold <= percentile; `{top} = max(1, 100 - percentile)`; `{s}` is "" when the value
    rounds to 1.
  - Debt types: the plan's rules on float32-cleaned values, the three percentile rules also need a positive raw
    value; defect_hotspot when D and E are the two largest totals and both positive. Triggered types are
    ordered by their family total (max of D and E for defect_hotspot, ties in `DEBT_TYPES` order), first two
    kept. Nothing triggered: the dominant family's type if its total is positive, else `()`.
- Deviations from the plan and why:
  1. Repository baseline for explanations. `shap_values` stays plain TreeSHAP (sums to `score - expected_value`),
     and `render_reasons` / `assign_debt_types` apply the plan's rules to whatever SHAP row they get, but
     `explain()` centres the SHAP values on the mean of the analysed repository by default (`baseline="model"`
     keeps the plan's behaviour). Priority is a percentile within one repository, and LambdaMART only learns
     score differences within a query, so a repository's overall score level (and the SHAP mass that encodes
     it, including repository-level features such as pkg_test_ratio) is arbitrary. With the model baseline 115
     of 900 High files and 1 Critical file had no reason and every High file showed a mitigation; with the
     repository baseline every High and Critical file has a reason (table below). One row is its own mean, so a
     single-row call uses the model baseline.
  2. `expected_value` comes from XGBoost's TreeSHAP bias column, not `TreeExplainer.expected_value`, which is
     wrong right after construction with shap 0.54.1 and XGBoost 3.4.1 (8.6e-09 instead of 0.0857 for the dev
     ranker; shap's loader misses the learned base score). Using it would break additivity by 0.086.
  3. `shap_values` always passes `tree_limit=-1`: shap's default is `best_iteration + 1` rounds when the booster
     carries that attribute, while `Ranker.score` uses every round (additivity error 2.67 otherwise on a booster
     with `best_iteration=9`). `check_additivity=False` at runtime; the tests assert additivity instead.
  4. "Pick the feature (raw or pct) with the largest phi" is read as the largest `phi[x] + phi[pct_x]` per base
     feature: raw and pct carry the same information and the model splits credit between them arbitrarily; it
     also matches `family_totals`.
  5. Values are cleaned to float32 before display and before every debt-rule comparison; otherwise the plan's
     own boundaries flip (`dup_ratio` stored as 0.1 is 0.10000000149 as a float64 and would trigger "> 0.10";
     `pct_satd_density` 0.9 is 0.89999998 and would not trigger ">= 0.9").
  6. Template schema: the plan's keys plus the `{s}` plural field, an optional `exact` list of `[value, sentence]`
     pairs (pairs, not a mapping, so the save_bundle round trip keeps numeric values), adjective lists that must
     cover 0..100 (last threshold 0), and mitigations that use `{adj}` too. SHAP signs are relative to a
     baseline, so a mitigation can come from a file above the median; fixed claims such as "Rarely changed" would
     then be false, while percentile adjectives stay true. `validate_templates` is strict (unknown keys and fields,
     conversions, attribute access and nested fields rejected; every sentence must render to one printable line
     without braces, pipes or angle brackets), and `Explainer` validates at construction.
  7. The percentile debt rules (`pct_hidden_coupling`, `pct_betweenness`, `pct_author_entropy`) also require a
     positive raw value: tied zeros get an average-rank percentile and a lone file has pct 1.0, which would label
     every single-file repository with architecture and knowledge debt.
  8. The no-trigger fallback maps the dominant family only when its total is positive; otherwise `debt_types` is
     `()` (the contract allows an empty tuple).
  9. Debt type order uses the family total (max of D and E for defect_hotspot); triggered types are kept
     whatever the sign of their total, as the plan says.
  10. Mitigations: at most one, independent of `max_reasons`.
  11. Additions beyond the plan's names: `Explanation`, `Explainer.explain`, `Explainer.expected_value`,
      `feature_totals`, `render_text`, `load_templates`, `validate_templates` and the constants, so P5.2 does not
      re-implement the glue and P5.3 gets per-feature values. `phi_row` is typed `npt.ArrayLike` (wider).
  12. shap and xgboost are imported lazily inside `Explainer.__init__`.
  13. NaN policy: `shap_values` accepts NaN (missing, like `Ranker.score`); `explain`, `render_reasons` and
      `assign_debt_types` reject non-finite feature values (P2.7 guarantees complete rows).
  14. Texts are one ASCII line without "|", "<", ">" or dashes; British "analysed" as elsewhere; reason
      templates end with "(top N% in repo)" while mitigations and the inverted test features do not.
  15. Templates always come from `bundle.reasons` (bundle file, else the package default); a bundle whose
      reasons.yaml is empty or incomplete is rejected by `Explainer`.
  16. Branch `step/P3.5-shap-explainer-reasons-and-debt-types` (given by the orchestrator) instead of
      `step/P3.5-explain`.

- Known issues / limitations:
  - Adjectives and "top N%" are percentile based, so in tiny repositories "Very high" can describe small absolute
    numbers, and the top file of a 12-file repository reads "top 1%" (`top = max(1, 100 - percentile)` as the
    plan says, with `pct = rank / n`).
  - Texts quote the default windows (90 days, 6 months, 5% of commits); custom settings are not reflected.
  - Reasons explain the ranking relative to the repository, not the absolute risk; under the repo baseline a
    file of an all-clean repository can still get reasons.
  - The repo baseline assumes `X` is exactly one repository snapshot; mixing repositories in one call centres on
    the wrong mean.
  - `Explanation` holds dicts, so it is not hashable.
