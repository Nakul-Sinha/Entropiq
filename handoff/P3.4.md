- Deviations from the plan and why:
  - D1. The command is a plug-in module (15.4).
  - D2. The evaluation curve is fitted on the embargoed training rows from `temporal_split`. These are the out-of-fold rows whose label window closes by their repository's last snapshot: 15,980 rows and 100 queries. It is tested on each repository's last snapshot (3,798 rows, 20 queries). P3.3 suggested fitting on every non-test row. But the label windows of the two snapshots just before the test snapshot overlap the test window, so this follows P3.1's temporal rule instead.
  - D3. Ranges use a repository bootstrap by default. Each refit draws the 20 repositories with replacement. The curve itself is still P3.0's `IsotonicCalibrator.fit` with `n_boot=0`, and the 5th and 95th percentiles are clamped the same way. `--bootstrap row` reproduces P3.0's row bootstrap exactly (tested). The reason: rows are clustered (the same file at several snapshots, base rates of 1% to 50% by repository). A row bootstrap gives a mean band width of 0.029 against 0.083, which understates the uncertainty about 3 times. P3.0's file is not edited.
  - D4. The shipped `calibrator.json` is refitted on all 27,208 OOF rows after evaluation. Those rows have the same parameters and score scale as the production booster `model/ranker.json`, which was trained on every row. The reported numbers belong to the embargoed evaluation curve.
  - D5. "Next to the MLflow run" means each model's existing LOPO run gets `model/calibrator.json`, the record, reliability table, summary and figure, plus `calibration_*` metrics and tags. They go through `MlflowClient.log_artifact` and `log_batch`, so no new run is created and the status (FINISHED), end time and params stay unchanged. Settings go to tags because params are immutable, which makes reruns safe: tags are overwritten and the latest metric value wins.
  - D6. More metrics than the plan asks for:
    - Brier skill against the training base rate
    - AUC-PR
    - 95% repository bootstrap intervals for every pooled metric
    - per-query Brier, ECE and AUC-PR
    - a second check that runs the final temporal model's test scores (`<model>_scores_temporal.parquet`) through the same evaluation curve

    The gate number is the pooled primary ECE.
  - D7. The figure is `results/figures/reliability.png` for the default model, as the plan names it. Other models get `figures/<model>_reliability.png`. Figures are drawn at 200 dpi (P3.6's rule) with `matplotlib.figure.Figure`, so pyplot and the global backend are never touched.
  - D8. The monotone variant is calibrated too: a few seconds of compute, and it lets P3.7 choose either model.
  - D9. Isotonic extremes are left as they are (see known issues). A Wilson floor on the bands was tried and rejected: it widened 34% of the bands.
  - D10. ECE is P3.1's equal-width 10-bin ECE (pooled over all test files). `CalibrationOutcome` gained `final_stats` (the shipped curve applied to every row), which the record, summary and MLflow payload need.

- Known issues / limitations:
  - Per-query ECE (about 0.13) is much higher than pooled ECE (0.010). LambdaMART margins carry no repository-level offset, so risk is a pooled probability that is not adapted to a repository's own base rate (1% to 50%). It is well calibrated across the population of files but can be off by several points within one repository.
  - At the isotonic extremes the curve is flat at exactly 0.0 (the lowest ~2% of scores) and 1.0 (the top ~0.03%), and the band collapses there (17 rows for the ranker). This is a known isotonic property, and it is documented in the summary.
  - The range shows the uncertainty of the pooled curve (90%, repository bootstrap). It is not a prediction interval for one file's outcome.
  - The ECE interval sits mostly above the point value because ECE is non-negative and biased upward in resamples; the summary says so.
  - `/work/code-P3.4` stays on the box for reproduction. No jobs are running there.
